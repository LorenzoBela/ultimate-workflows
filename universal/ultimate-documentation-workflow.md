# Ultimate Documentation & Onboarding Workflow

This workflow guides the planning, creation, and synchronization of codebase documentation, technical specifications, and developer setup guides to ensure onboarding friction is zero and architecture is clear.

---

## The 4-Phase Documentation Pipeline

### Phase 1: High-Level Repository Architecture (README)
*   **Action:**
    1. Maintain a master repository `README.md` at the root of the project. Every project must clearly state:
       *   **Project Goal:** What does the codebase accomplish?
       *   **Prerequisites:** Required language runtimes, OS constraints, database setups, and global packages.
       *   **Setup Checklist:** Concrete commands to clone, configure, build, and test locally.
       *   **Directory Structure:** A high-level directory map showing where features, components, tests, and configurations reside.
       *   **Run Commands:** How to start the dev server and build production assets.
    2. Align the README tone and formatting with `Brand Voice & Identity System` voice guidelines.
    3. Use `concise-planning` to generate an atomic checklist for documentation tasks.

### Phase 2: API Specification (OpenAPI / Swagger)
*   **Action:**
    1. Document API interfaces using standardized **OpenAPI/Swagger specs** (YAML or JSON) or autogenerated routers (like FastAPI OpenAPI or tRPC routers).
    2. Define request query params, request body payload types (with validation rules), response formats, success models, and failure payloads (e.g. ValidationError, UnauthorizedError).
    3. Include example payloads for all key endpoints to aid integration.
    4. Use `supabase-mcp-server/list_tables` to auto-generate database entity documentation.
    5. Use `supabase-mcp-server/get_project_url` and `get_publishable_keys` to document API base URLs and public keys.

### Phase 3: Architectural Documentation & ADRs
*   **Action:**
    1. Maintain an Architecture Decision Records (ADR) system under `docs/adr/`. Each ADR must log the context, decision, consequences, and tradeoffs.
    2. Maintain code docstrings. Document *why* complex algorithms or constraints are implemented, rather than *what* the code does.
    3. Avoid stale comments: update comments immediately when changing related business logic.
    4. Use `docx` for generating formal Word document exports of architectural documentation.
    5. Use Data Presentation & Deck Layouts for creating HTML slide decks summarizing architecture for stakeholder presentations.

### Phase 4: Developer Onboarding & Dev-Ops Guide
*   **Action:**
    1. Draft setup guides detailing environment variables, mock payloads, seed data scripts, and third-party dashboard setups.
    2. Maintain a clean, updated `.env.example` file containing dummy values for all required environment variables.
    3. Outline the deployment pipeline: how changes promote from branch → PR → staging → production.
    4. Use `firebase_get_sdk_config` and `get_publishable_keys` to document SDK configuration requirements for new developers.
    5. Apply Design Theme Presets for branded, visually appealing onboarding documentation.

## Cross-Cutting Concerns
*   **Research:** Use Web Search, Web Extraction Tool, and official library documentation for API documentation standards and best practices.
*   **Memory:** Use Persistent Project Memory / Scratchpad to persist documentation structures and decisions across conversations.
*   **Linting:** Use Strict Linting & Type Validation to verify code examples in documentation compile and run correctly.
*   **Banner Design:** Use Hero Graphic & Banner Design for creating branded documentation headers and social preview images.
